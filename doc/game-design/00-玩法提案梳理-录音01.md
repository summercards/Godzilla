## 0. 先说结论：这份提案改的是产品定义，不是功能

构想方的原话是「虽然是挂机，但挂机里头还是得有一定的策略，这样它的养成才会有对应的有效性」。
目标清楚、方向对。但**达成手段里有三条直接踩在铁律上** —— 按 `SOUL.md` 的边界，
`tv/` 的定位改动必须显式提出，不能顺手改：

| # | 提案原话 | 撞到哪条铁律 | 严重度 |
| --- | --- | --- | --- |
| E1 | 「怪兽要不要血条？**怪兽要血条**」 | `SOUL.md` / `USER.md`：**无血条、无死亡、无玩家操作，任何设计不得引入失败状态** | ⚠️⚠️ **产品定义级** |
| E2 | 「失败了你就得**重新来**」「它会影响你的**关卡进度**」 | 同上：不得引入失败状态 | ⚠️⚠️ **产品定义级** |
| A4 | 「那个位置是你可以去摆。你可以让他先放哪个、后放哪个，**这个就变成他的一个策略**」 | 同上：**无玩家操作** | ⚠️ **需重新定义"操作"边界** |

**这三条不是"做完再说"的优化项，是"要不要改产品"的决策项。** 我的判断：

- **E1 + E2 我建议否决。** 理由不是"跑题"，而是**成本与收益不成比例**：为让"失败"成立，
  必须同时引入血条、受击掉血、判负、复活/回退、进度保护 —— 而现有的 Boss 血量
  （`bossMaxHp()` 按目标击杀时长反解，`tv/DESIGN.md` § 关底 Boss）整套设计哲学就是
  **"锚在巨兽自己的输出上，保证每一档等级都稳定落在 ~60 秒"**，即**"不会被设计成打不过"**。
  加失败等于把这条已经标定过的链条整条重写，且**产品会从"电子鱼缸"变成"要盯着的游戏"**。
- **A4 有解，不必否决。** "排序"可以不交给玩家：把顺序做成**可从若干预设打法里选的策略模板**
  （例：清怪型 / 破甲型 / 保命型），选择频率极低（一次流派取向），不构成"操作"。
  真正要守的是"**不出现需要持续输入的界面**"。这条我建议在文档里正名后再做。

> 换句话说：**P0 的活可以在铁律内全部做完**（战斗系统骨架 + 元素通电 + 关卡循环微调），
> 只有"血条/失败"必须主人拍板。

## 1. 会议摘要

**一句话：** 想给挂机加"策略 → 养成才有意义"这一层，手段是
**技能卡牌时间轴 + 元素反应 combo + 属性克制 + 4~5 分钟一局的关卡循环 + 血条失败惩罚**。

按时间序：

| 时段 | 议题 |
| --- | --- |
| 00:02–01:51 | **技能卡牌时间轴** —— 普攻为底，技能视为一张张卡牌；后台有进度条/充能，轮流释放；槽位随等级解锁（1 → 3~5）；**空槽 = 只能普攻 = 效率低** |
| 01:03–01:51 | **元素 combo** —— 火→（目标烧着）→再火 = 爆炸；火→水 = 气化；毒+火 = 爆炸。"配技能"本身成为追求目标 |
| 01:52–03:37 | **属性 → 体貌 → 克制** —— 主加哪条属性身体就变；Boss 与小怪带属性逼换配置；城镇防御带属性（铁皮/混凝土/加固），伤害随克制上下浮动 |
| 03:44–04:20 | **多怪兽架构** —— 卡牌绑怪物；金刚可作第二只怪；结构复用、技能独立；「PvP 都可以设计」 |
| 04:20–06:08 | **关卡循环 + 失败** —— 失败影响关卡进度、放置游戏有手点成本；单图 4~5 分钟一轮、打完从头；越深爆箱概率与奖励越高；通到底必得特定奖励；天赋点可缩到 3 分钟（快速 reload） |
| 06:12–08:06 | **分期口径 + 参照** —— 协作方定调「先把技能做出来…从伤害类型去考虑」；构想方同意「先加叠加伤害/击退/爆炸，属性属进阶」；参照横版挂机：弓手=速+暴击 / 法师=AOE / 战士=防御击退 |
| 08:06–11:15 | **时间轴的实质** —— 明确"进度条 = 充能轴"、"像有费的概念"、类比 DOTA 传奇技能位；**协作方最后再次强调「两个东西可能要先加，一个是失败条件」** |

**唯一分歧**：协作方把"失败条件"列为要先加；构想方归到"进阶"。**这条分歧正是第 0 节的冲突源头。**

## 2. 按游戏功能大类的归类 ★ 核心

**读法：** 22 条提案全部收进下列七个大类。每个大类标注性质 ——
**【新功能】** = 项目里没有、要从零建；**【功能优化】** = 已有基础、需扩展或补全。
大类内若混合两种性质，在标题下点明。

| 大类 | 性质 | 包含提案 | 优先级 |
| --- | --- | --- | --- |
| **一、战斗系统** | **【新功能】**（含 1 项优化） | 技能卡牌轴 · 技能槽 · 充能时间轴 · 空槽降级普攻 · 伤害类型扩展 · **元素反应（优化）** · 策略模板 | **P0 / P1** |
| **二、属性与克制系统** | **【新功能】** | 城镇防御属性 · 敌人带属性 · 克制倍率 · 伤害数字表现 | **P1 / P2** |
| **三、关卡与循环系统** | **【功能优化】** | 单局循环 · 深度奖励 · 通关大赏 · 快速 reload | **P1 / P2** |
| **四、成长与养成系统** | **【功能优化】** | 主属性 → 体貌 · 数值长期调优 | **P1 / P0** |
| **五、角色与怪物系统** | **【新功能】** | 多怪兽架构 · 技能与怪物解耦 | **P2** |
| **六、风险与失败机制** | **【新功能】· 撞铁律** | 怪兽血条 · 失败惩罚 · 手点成本 | **裁决项** |
| **七、多人系统** | **【新功能】· 建议搁置** | PvP | **P3** |

**分类小结：**

- **【新功能】4 个大类**（战斗 / 属性克制 / 角色怪物 / 多人），共 12 条 —— 其中 7 条集中在战斗系统。
- **【功能优化】2 个大类**（关卡循环 / 成长养成），共 6 条 —— **与现有实现重合度最高，改动量最小**。
- **【撞铁律】1 个大类**（风险与失败），3 条 —— **唯一被卡死的部分**。
- 另有 1 条跨类的工作方式（数值长期调优），归入成长养成。

**两条已当场达成一致、直接采纳的工作原则**（不是功能，不进大类）：
**G3** 参照横版挂机三原型：**速+暴击 / AOE 群伤 / 防御击退**（技能取材库）·
**G4** 先做**叠加伤害 / 击退 / 爆炸**，属性克制后上。

## 3. 逐大类详解：原话 → 现状映射 → 差距

### 一、战斗系统 【新功能 · 含 1 项优化】

**提案原话**（01:51）「空着的位置…它就会比较弱一些」「技能越多效率越高」；
（10:46）「这是自动的，但那个位置是你可以去摆」。

**⚠️ 这里有一处必须先正名的概念冲突：**

| | 现有「技能树」 | 提案的「技能卡」 |
| --- | --- | --- |
| 位置 | `progression.js` `SKILLS`，3 分支 9 节点 | 无 |
| 性质 | **被动增强**（强化既有 6 个动作） | **主动技**（新的释放单元） |
| 获取 | DNA 解锁，一次性 | 装配到槽位，随等级扩槽 |
| 存档 | `data.skills`（已登记 id 白名单） | 无 |

> **两套"技能"同名不同物。** 现有 6 个动作是**固定状态机**
> （`walk/claw/stomp/tail/roar/beam`，决策优先级见 `游戏逻辑梳理.md` § 4.1），
> 冷却由动作自身持有。提案的卡牌轴要**接管"什么时候放什么"这个决策权** ——
> 所以这是**替换**现有 AI 决策层，**不是叠加**。两者不能共存，实现前必须先定取舍。
> 建议命名区分：现有 9 节点叫**「进化技能」**，新卡牌叫**「战技」**，避免存档字段撞名。

**包含条目：**

| 条目 | 性质 | 现状 | 差距 |
| --- | --- | --- | --- |
| 技能卡牌轴（主动技） | 新功能 | ❌ 无主动技系统 | 需新建技能定义与释放单元 |
| 技能槽随等级解锁（1 → 3~5） | 新功能 | ❌ 无 | 需槽位数据结构 + 存档字段 |
| 充能时间轴（背景运行、自动释放） | 新功能 | ⚠️ 只有各动作自己的 `cd`，无共享时间轴 | 需充能调度器 |
| 空槽降级普攻 | 新功能 | ❌ 最低档是爪击，无"普攻"概念 | 需一个可无限重复、不占槽的填充动作 |
| 伤害类型扩展（叠加 / 击退 / 爆炸） | 新功能 | ⚠️ 已有 6 动作各自的伤害，无"叠加/击退/爆炸"这层标记 | 轻量，可在现有伤害入口加标记 |
| **元素反应 combo** | **功能优化** | ⚠️ 管道已铺好、**没通电**（见下） | **救活已有死数据** |
| 策略模板（替代玩家排序） | 新功能 | ❌ 无 | 3~4 个预设流派，低频选择 |

**元素反应 —— 全案性价比最高的一块（"通电"而非"新建"）：**

| 现成的东西 | 位置 | 状态 |
| --- | --- | --- |
| `subElements[]` 字段 | `progression.js` / 存档 | ✅ 已存在、已落盘 |
| 主元素判定 `mainElement()` | `progression.js` | ✅ 生效 |
| 副元素消费 | `game.js:329` | ⚠️ **只有 `'pyro'` 一个 key 被读** |
| 连锁传导通道 `chain` | `game.js` `updateBeam` | ✅ 已有先例：280px 内最多 2 目标 ×0.4，带电弧 |

> `e_spark / e_frost / e_magma / e_venom` 这 4 条突变**抽到了什么都不做**
> （`变异视觉效果对账.md` § 一，判定 `inert`）。元素反应是"接通消费端"，
> 顺手救活 4 条死突变 + 4 个空壳天赋 —— 这是**功能优化**，不是新功能。

**差距：** 缺**目标状态容器**（现在没有任何 `{element, stacks, until}`）·
缺**二元反应表与倍率**· 需要一条**会失败的断言**（`subElements` 每个 key 必须能找到消费点）·
⚠️ "水"目前不在元素环里，需裁决（新增水系 **或** 映射到 `cryo`）。

### 二、属性与克制系统 【新功能】

**提案原话**（03:16）「打了这个城镇，它有防护了，比如铁皮、混凝土、加固…
你打的时候那个数字，如果克制它，100、130 就上升，如果不是，120 实际上是下降的」。

| 条目 | 性质 | 现状 | 差距 |
| --- | --- | --- | --- |
| 城镇防御属性（铁皮/混凝土/加固） | 新功能 | ❌ 建筑只有 `layer / hp / dead` | 需新增 `elem` 字段 + 资产侧标注 |
| 敌人带属性（小怪 / Boss） | 新功能 | ❌ 10 种敌人只有 `hp / resistance` | 同上 |
| 克制关系 → 伤害浮动 | 新功能 | ❌ 无克制概念 | 需 `COUNTER[攻击][目标]` 表 |
| 伤害数字表现 | 新功能 | ❌ 无伤害数字（受击只有 `recoil / hitFlash / shake`） | 需新表现层 |

**⚠️ 伤害数字的包装风险：** 这个产品外壳是**GNN 新闻直播**（机位条 / 滚动新闻条 / 现场档案），
画面里弹伤害数字会**破坏"这是被拍的现场"这层幻觉**。两个折中方向：
① 数字只出现在**观测面板**（那里本就是监控读数），战斗画面不弹；
② 战斗画面弹，但**套一层"军事分析 HUD"样式**（像素描边 + 等宽字），看起来像新闻台的图形包装。
**需裁决。**

### 三、关卡与循环系统 【功能优化】

**提案原话**（05:07）「一张地图它有进度条…越打到后边，爆箱概率更高、奖金币更多…
打完了以后它又从头开始」；（05:52）「大概 4 分钟左右，天赋可以缩短到 3 分钟」。

**这一大类与现有实现重合度最高（约 80%）：**

| 条目 | 性质 | 现状 | 差距 |
| --- | --- | --- | --- |
| 单图进度条 | **已有** | ✅ `drawCampaignRoute()` 5 段条（`w=560, h=8, y=26`），填充长度表达本区推进度 | **不用做** |
| 进度由什么驱动 | **已有** | ✅ `mapProgress() = min(1,Δ建筑/12)×0.6 + min(1,Δ敌军/8)×0.4`，满 1 开闸锁存 | **已在** |
| 单局循环（4~5 分钟一轮） | 优化 | ⚠️ **结构相反**：现在是**无尽推进**（`appendWorldChunk()` 无限铺，`d ≥ 11` 恒定纽约） | ⚠️ **根本性结构变更** |
| 越深奖励越高 | 优化 | ❌ 拆楼收益 `30+楼高×0.11` **不随本局进度变** | 需一层"本局深度"倍率 |
| 打通必有特定奖励 | 优化 | ⚠️ 部分：推进时 `grant(180+d×30)` + `dna += 2` | 需**"通关大赏"**这一档 |
| 快速 reload（天赋缩短单局） | 优化 | ⚠️ `巨躯动能`已提速、`不可阻挡`已降压制 | 要的是**"一轮结束立即开下一轮"**，不是走得快 |

> **⚠️ 结构变更的连带影响：** 现在地图**无限延伸**，区域编号是唯一进度轴。
> 改成"一局一图"意味着章节映射（1–5 大阪 / 6–10 东京 / 11+ 纽约）、
> 阶段门槛（2600m / 7200m）、敌人分档池**全都挂在区域编号上** —— 是改一条主轴。
>
> **低成本解法（建议）：** 不推翻无尽推进，把"一局"定义为**"5 个区域 = 一章"**，
> 章末（区域 5 / 10 / 15…）给通关大赏。这样进度条天然是已有的 5 段推图条、
> 章节换场（雪花转台）天然就是"下一轮开始"。**成本从"高"降到"中"。**

### 四、成长与养成系统 【功能优化】

| 条目 | 性质 | 现状 | 差距 |
| --- | --- | --- | --- |
| 主属性 → 体貌变化 | 优化 | ✅ **已实现**：`mainElement()` → `beamColor()` / `elementColor()`；突变 `hue` → 五档皮肤；`appearance.js` 是"形态→部件槽→{样式,颜色,大小}"框架 | 目前**只有主元素影响吐息色与背鳍色**；"加得越多身体变越多"的**分级外观**没有（现接近开关量） |
| 数值长期调优 | 优化 | — | **不是功能，是工作方式**（见下） |

> **"主属性 → 体貌"是又一个"通电"项**：`growth.js` 的 `hueStyles` 只有 4 个值，
> 而赋值有 6 处，导致"炎狱体 = 赤化""冰封体 = 翠化"外观撞车（`变异视觉效果对账.md` § 四）。
> 提案的"主属性决定体貌"正是**把 `hue` 从枚举改成色相偏移量**的契机 —— 一次解决两件事。

> **数值长期调优（协作方 04:20「数值这个要调，而且是长期玩的过程」）** ——
> 按 `SOUL.md`「数值必须给公式，不给魔数」，每套新数值都必须：
> ① 公式写进 `tv/DESIGN.md`；② 有一条**会失败的断言**钉住；
> ③ 有 `.workbuddy/` 下的无头探针可复测（现有 `_boss-ttk.cjs` / `_route-metric.cjs` 是先例）。

### 六、风险与失败机制 【新功能 · 撞铁律 · 裁决项】

## 4. 优先级评估

**排序规则（按重要性降序）：**

1. **撞铁律的一律不进队列**，先裁决 —— 否则做完再推翻，成本翻倍。
2. **"通电"优先于"新建"** —— 已有管道但没接消费的，性价比最高。
3. **是别人前提的先做** —— 战斗系统的技能卡是策略模板、元素反应、技能解耦的前提。
4. **与现有实现重合度高的先做** —— 关卡循环重合 80%，改动量远小于听起来。
5. **纯表现层最后做** —— 伤害数字，等数值定型再上。
6. **远期架构与新怪兽搁置**。

**按大类排定：**

| 大类 | 性质 | 优先级 | 能立刻开工吗 |
| --- | --- | --- | --- |
| 一、战斗系统 | 新功能（含 1 优化） | 技能卡骨架 **P0** · 元素反应 **P1** | ✅ 可以，**不撞铁律** |
| 二、属性与克制 | 新功能 | **P1 / P2** | ⚠️ 依赖一次包装裁决（伤害数字） |
| 三、关卡与循环 | 功能优化 | **P1**（章=一局方案）/ **P2** | ⚠️ 需一次结构裁决 |
| 四、成长与养成 | 功能优化 | 数值调优 **P0** · 主属性→体貌 **P1** | ✅ 可以 |
| 五、角色与怪物 | 新功能 | **P2** | 依赖战斗系统 |
| 六、风险与失败 | 新功能·撞铁律 | **裁决项** | ❌ **必须先拍板** |
| 七、多人 | 新功能 | **P3 搁置** | ❌ 建议不做 |

> **一句话总结：** 提案里**真正卡死的只有第六类"风险与失败"**。其余六大类共 19 条
> 全部可以在维持"无血条、无死亡、无持续操作"的前提下落地 ——
> 因为策略性不来自"失败惩罚"，而来自**"配什么卡、什么顺序"本身**。
> 这一点我建议当面跟构想方对齐：**策略感 ≠ 风险感**。

## 7. 数值框架初稿

> 按 `SOUL.md`：**数值必须给公式，不给魔数。** 以下公式中的**标定系数**
> （形如 `CAL`）都是占位，必须在实现时用无头探针实测标定，标定过程与结论
> 一并写进 `tv/DESIGN.md`，并配一条会失败的断言。

### 7.1 战技槽与充能轴（战斗系统）

```js
// 槽位数：复用现有形态档锚点，不新造等级门槛
slots(L)   = clamp(1 + floor((L - 1) / 25), 1, 5)      // L1=1 · L25=2 · L50=3 · L75=4 · L100=5

// 充能轴：每个槽独立充能，到点即可释放；同一拍多个可用时按槽序取第一个
charge_i  += dt × chargeRate_i                          // 每帧推进
ready_i    = charge_i >= cost_i
charge_i   = 0                                          // 释放后归零

// 空槽与未就绪时降级为普攻（普攻不占槽、无充能）
if (无槽可用) 执行基本攻击

// 效率 = 有卡覆盖的时间占比（这就是"技能越多效率越高"的机制表达）
efficiency(L) = Σ(已装配且已就绪的槽) / slots(L)
```

**调参旋钮：** `chargeRate_i`（充能速度）与 `cost_i`（一次充能代价），两者合成"每隔几秒放一次"，
对应录音里「像有费的概念」。**初始基准建议：** 普攻间隔沿用现有爪击节奏（1.18s / 0.54s 命中）；
战技间隔从 `cost/chargeRate ≈ 4~6s` 起调，**具体值待实测标定**。

### 7.2 元素反应（战斗系统 · 优化项）

```js
// 附着：命中时给目标挂状态（不落盘，不进存档）
target.status = { element, stacks, until: now + STATUS_TTL }

// 二元反应表：先附着 A，再命中 B
REACT[A][B] → { name, mult, aoe, ... }

// 倍率统一入口
reactMult = REACT[A][B].mult × (1 + 0.06 × 相关天赋等级)
```

**反应表初稿**（`mult` 待标定；`aoe` 复用现有 `chain` 的 280px / 2 目标通道）：

| 先（附着） | 后（命中） | 反应 | 效果方向 |
| --- | --- | --- | --- |
| `pyro` 火 | `pyro` 火 | **爆燃** | 单点爆发（对已烧着目标） |
| `pyro` 火 | `cryo` 冰 | **气化** | 范围伤害 + 击退 |
| `venom` 毒 | `pyro` 火 | **爆燃** | 爆发 + 持续伤害 |
| `volt` 雷 | `cryo` 冰 | **导电** | 连锁至邻近目标 |
| `magma` 熔核 | `cryo` 冰 | **碎裂** | 破防（对高耐久目标额外） |

> 表中"水"按 Q5 建议映射到 `cryo` 冰棘；`radiant` 辐热暂不参与反应（作为中性元素）。

### 7.3 属性克制（属性与克制系统）

```js
// 目标属性：建筑/敌人新增 elem 字段，资产侧标注
// 攻击属性 = 怪兽主元素（mainElement()，已有）
mult = COUNTER[攻击.elem][目标.elem]        // 默认 1.0
finalDamage = power() × mult
```

**倍率卡**（结构固定，数值待标定）：克制 `1 + k` · 被克 `1 − k` · 无关 `1.0`。

**防御属性初稿**（`k` 待标定，建议起调 `k = 0.3`）：

| 城镇防御 | 被克制（×1+k） | 抗性（×1−k） |
| --- | --- | --- |
| 铁皮 `steel` | `volt` 雷 | `pyro` 火 |
| 混凝土 `concrete` | `magma` 熔核 | `cryo` 冰 |
| 加固 `reinforced` | `venom` 腐毒 | `radiant` 辐热 |

> ⚠️ 上表是**结构示例不是定稿**。定稿前要满足：6 元素 × N 防御 全表覆盖、
> 每个防御至少 1 克制 1 抗性、不存在"无解防御"。

### 7.4 关卡循环（关卡与循环系统）

```js
// 一局 = 一章（5 个区域），章末结算
runMax      = 5                                       // 复用现有"一章 5 区"
T_target    = 240                                     // 秒，录音里的"4 分钟左右"
reloadSpeed = 1 + 0.08 × 快速装填天赋等级              // 满级 ≈ ×1.33 → 240 / 1.33 ≈ 180s = 3 分钟
T_clear     ≈ T_target / reloadSpeed

// 本局深度奖励（对应"越往后奖励越多"）
depth = 本局已推进区域数 / runMax                      // 0 → 1
奖励倍率 = 1 + DEPTH_GAIN × depth                      // 拆楼与击破收益都乘它
```

**章末通关大赏**：`depth === 1` 时发放一次性奖励（对应"不打到底就拿不到"）。
**形态沿用现有 `grant()`**，不新增发钞口。

> ⚠️ 现有单局（一区）实际耗时**未实测**。开工前第一步应当用无头探针
> （参照 `.workbuddy/_boss-ttk.cjs`）量出当前值，再反解 `T_target` 的调参方向。

### 7.5 若主人仍决定做失败条件（风险与失败 · 不推荐）

## 8. 存档影响评估 ⚠️

按 `游戏逻辑梳理.md` § 9.3：**存档版本是最危险的地方** ——
`progression.js` 当前 `version: 4`，`sanitize()` **同时接受 3 和 4**，
只把版本号改成 5 就等于把所有旧档判废、回落成 1 级、**且不报错**。

| 大类 / 条目 | 新字段 | 是否必须升版本 |
| --- | --- | --- |
| 战斗系统 · 技能卡轴 | `warbuild`（槽位装配与策略模板） | 是（4 → 5） |
| 战斗系统 · 元素反应 | 复用已有 `subElements` | **否** |
| 成长养成 · 主属性→体貌 | 复用已有 `hue` / `morph` | **否** |
| 属性克制 · 敌方属性 | 资产侧标注，不进玩家存档 | **否** |
| 关卡循环 | `runProgress` / `runRewards` | 是（4 → 5） |
| 风险失败 · 血条 | `hp` / `runLost` | 是（4 → 5） |

**硬约束（三条，缺一不可）：**
1. `sanitize()` 必须**同时接受 4 和 5**，旧档就地补默认值 —— **绝不判废**。
2. 任何派生种子必须**确定性**：沿用 `hashSeed(...)`，**禁用 `Math.random()` / `Date.now()`**。
3. 新字段一律**钳制**取值范围，入 `sanitize()` 的白名单。

**另需一条会失败的断言**（现有 `tests/tv.test.cjs` 是先例）：
**存档键两侧必须是同一个字符串** —— 任何新增字段都要确认
`tv/game.js` 的 `SAVE` 与 `tv-preload.js` 的 `KEY` 仍然一致，
否则接管**静默失效**、进度写回 localStorage 而两端不报错。
