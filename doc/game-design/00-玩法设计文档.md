# 巨兽都市 · 玩法设计文档

> **状态：设计中 · 2026-09-30**
> **范围：** 技能体系、属性克制、关卡循环三条主线的扩展设计。
> **前提 —— 三条产品铁律，本文所有设计必须服从：**
> **无血条、无死亡、无玩家操作；任何设计不得引入失败状态。**
> 第六节「风险与失败机制」违反该前提，已列为**待决策事项**，未裁决前不进入实现。
>
> **归类约定：**
> **【新功能】** = 项目里没有、要从零建 · **【功能优化】** = 已有基础、需扩展或补全。
> 优先级 **P0** 立即可开工 · **P1** 第一期 · **P2** 第二期 · **P3** 搁置。

**两条贯穿全程、直接采纳的设计原则**（不是功能条目，不进大类）：
**参照横版挂机三原型** —— 速+暴击 / AOE 群伤 / 防御击退（技能取材库）·
**先做叠加伤害 / 击退 / 爆炸，属性克制后上**。

## 一、战斗系统 【新功能 · P0 / P1】

### 设计内容

把"什么时候放什么技能"从固定的动作状态机，扩展成一套**可配置、可成长、可组合**的
主动技能体系，让养成有对应的策略空间。

- 技能以**卡牌**形式存在，装配到**技能槽**中。
- 每个槽**独立充能**，充能完成后在后台自动释放 —— **不引入操作输入**。
- 槽位随等级解锁，空槽降级为**普攻**。技能越多，输出效率越高。
- 技能之间可产生**元素反应**，配卡本身成为追求目标。
- 玩家不手动排序，改为从**预设策略模板**中择一。

### 系统构成

| 模块 | 说明 | 性质 |
| --- | --- | --- |
| 战技卡 | 可装配的主动技能定义 | 新建 |
| 技能槽 | 随等级解锁（1 → 5） | 新建 |
| 充能轴 | 每槽独立推进，到点自动释放 | 新建 |
| 普攻 | 不占槽、无充能的填充动作 | 新建 |
| 伤害类型 | 叠加 / 击退 / 爆炸等伤害标记 | 扩展 |
| 元素反应 | 元素状态的组合效果 | **优化** |
| 策略模板 | 预设打法，替代玩家手动排序 | 新建 |

### 命名约束 ⚠️

现有「技能树」（`progression.js` `SKILLS`，3 分支 9 节点）是**被动增强** ——
强化既有的 6 个动作，DNA 解锁、一次性、存入 `data.skills`。
本节的「战技卡」是**主动技** —— 新的释放单元。**两者同名不同物，必须分开命名：**

| | 现有 | 本次新增 |
| --- | --- | --- |
| 名称 | **进化技能** | **战技** |
| 性质 | 被动增强既有动作 | 主动释放单元 |
| 获取 | DNA 解锁，一次性 | 装配到槽位，随等级扩槽 |
| 存档字段 | `data.skills` | `warbuild`（新增） |

### 决策权归属 ⚠️

现有 6 个动作（`walk / claw / stomp / tail / roar / beam`）是**固定状态机**，
冷却由动作自身持有，决策优先级固定。充能轴要**接管"什么时候放什么"这个决策权** ——
因此这是**替换**现有 AI 决策层，**不是叠加**。两者不能共存，实现前必须先定取舍。

### 元素反应 —— 全案性价比最高的一块【功能优化】

**管道已经铺好，只是没通电：**

| 已具备 | 位置 | 状态 |
| --- | --- | --- |
| `subElements[]` 字段 | `progression.js` / 存档 | 已存在、已落盘 |
| 主元素判定 `mainElement()` | `progression.js` | 生效 |
| 副元素消费 | `game.js:329` | **只有 `'pyro'` 一个 key 被读** |
| 连锁传导通道 | `game.js` `updateBeam` | 已有先例：280px 内最多 2 目标 ×0.4，带电弧 |

「元素反应」不需要从零建，而是**接通消费端** —— 顺手救活 4 条完全失效的突变
（`e_spark / e_frost / e_magma / e_venom`）与 4 个空壳天赋。

### 改造范围

- 新建充能调度器（现有只有各动作自己的 `cd`，无共享时间轴）。
- 新建技能槽数据结构与装配/排序的存档字段。
- 新建「普攻」概念（现有最低档动作是爪击，1.18s / 0.54s 命中）。
- 新建目标状态容器 `{ element, stacks, until }`（现有无任何目标状态）。
- 新建二元反应表与倍率。
- ⚠️ 「水」目前不在元素环（现有为 pyro / volt / cryo / venom / radiant / magma），需决策。
- **需一条会失败的断言**：`subElements` 中每个 key 必须能找到消费点。

## 二、属性与克制系统 【新功能 · P1 / P2】

### 设计内容

给建筑与敌人引入**属性**，让"打什么用什么"成为长期策略，而不只是堆数值。

- **城镇防御带属性** —— 铁皮 / 混凝土 / 加固等，随推进逐步出现。
- **敌人带属性** —— 小怪与 Boss 各有属性，逼玩家调整配置。
- **克制关系** —— 伤害随克制上下浮动（克制上升、被克下降）。
- **伤害数字** —— 克制时打出更高的数字，让关系可读。

### 系统构成

| 模块 | 说明 | 性质 |
| --- | --- | --- |
| 城镇防御属性 | 铁皮 `steel` / 混凝土 `concrete` / 加固 `reinforced` | 新建 |
| 敌人属性 | 小怪与 Boss 的 `elem` 字段 | 新建 |
| 克制倍率 | `COUNTER[攻击][目标]` 查表 | 新建 |
| 伤害数字 | 战斗表现层 | 新建 |

### 现有基础

| 项 | 现状 |
| --- | --- |
| 建筑数据 | 只有 `layer / hp / dead`，**无属性** |
| 敌人数据 | 10 种单位只有 `hp / resistance`，**无属性** |
| 伤害反馈 | 受击只有 `recoil .1s` + `hitFlash .18s` + `shake`，**无伤害数字** |
| 攻击属性来源 | 已有 `mainElement()`（主元素）可直接复用 |

### 改造范围

- 建筑与敌人新增 `elem` 字段，**资产侧标注**（不进玩家存档）。
- 新建克制表，默认倍率 1.0。
- 新建伤害数字表现层。

### 表现层约束 ⚠️

产品外壳是 **GNN 新闻直播**（机位条 / 滚动新闻条 / 现场档案），
战斗画面直接弹伤害数字会**破坏"这是被拍到的现场"这层包装**。两个方向：

1. 数字只出现在**观测面板** —— 那里本就是监控读数，战斗画面不弹。
2. 战斗画面弹，但**套一层"军事分析 HUD"样式**（像素描边 + 等宽字），
   让它看起来像新闻台的图形包装。

## 三、关卡与循环系统 【功能优化 · P1 / P2】

### 设计内容

把"一局"显式化，形成"推进 → 结算 → 再来一局"的循环节奏。

- 单张地图有进度条，打完后从头开始。
- **越深奖励越高** —— 爆箱概率与金币奖励随本局深度递增。
- **通到底必得特定奖励** —— 不打到最后拿不到。
- 单局时长约 **4 分钟**；天赋点可缩短到 **3 分钟**（快速重开）。
- 失败会影响关卡进度（**见第六节，待决策**）。

### 现有基础 —— 与现状重合约 80%

| 条目 | 现状 |
| --- | --- |
| 单图进度条 | **已有**：`drawCampaignRoute()` 画 5 段条（`w=560, h=8, y=26`），填充长度表达本区推进度 |
| 进度驱动 | **已有**：`mapProgress() = min(1,Δ建筑/12)×0.6 + min(1,Δ敌军/8)×0.4`，满 1 开闸并锁存 |
| 推进结算 | **已有**：`grant(180 + d×30)` + `dna += 2` |

### 改造范围

| 条目 | 差距 |
| --- | --- |
| 单局循环 | ⚠️ **结构相反**：现为**无尽推进**（`appendWorldChunk()` 无限铺，`d ≥ 11` 恒定纽约） |
| 深度奖励 | 拆楼收益 `30 + 楼高×0.11` **不随本局进度变**，需"本局深度"倍率 |
| 通关大赏 | 需新增"通到底"这一档奖励 |
| 快速重开 | 现有 `巨躯动能`只提升走速，需的是**一轮结束立即开下一轮** |

### 结构方案 ⚠️

**方案 A（推翻）：** 一局一图，地图有限、打完重来。
代价：章节映射（1–5 大阪 / 6–10 东京 / 11+ 纽约）、阶段门槛（2600m / 7200m）、
敌人分档池**全部挂在区域编号上** —— 等于改一条主轴。

**方案 B（建议）：** 把"一局"定义为 **"5 个区域 = 一章"**，章末（区域 5 / 10 / 15…）结算。
优点：进度条天然复用已有的 5 段推图条，章节换场（雪花转台）天然就是"下一轮开始"。
**成本从"高"降到"中"。**

## 四、成长与养成系统 【功能优化 · P0 / P1】

### 设计内容

- **主属性 → 体貌变化** —— 主要加点集中在哪条属性，身体就往那个方向变化。
- **数值长期调优** —— 作为持续性的工作方式，不是一次性设计。

### 主属性 → 体貌

**现有基础：**

| 项 | 现状 |
| --- | --- |
| 形态框架 | `appearance.js`：怪物 → 形态 → 部件槽 → `{样式, 颜色, 大小}` |
| 主元素判定 | `mainElement()` → `beamColor()` / `elementColor()`（决定吐息色与背鳍色） |
| 体色 | 突变 `hue` → 五档皮肤（`clean / jade / frost / ember / void`） |

**改造范围：**

- 目前**只有主元素影响吐息色与背鳍色**，"加得越多变化越大"的**分级外观**没有（现接近开关量）。
- ⚠️ 顺带修一个已有缺陷：`growth.js` 的 `hueStyles` 只有 **4 个值**，而赋值有 **6 处**，
  导致"炎狱体 = 赤化""冰封体 = 翠化"**外观撞车**。
  本次可将 `hue` 从枚举改为**色相偏移量**，一次解决两件事。

### 数值长期调优（工作方式）

按「数值必须给公式，不给魔数」的既定纪律，每套新数值都必须满足三条：

1. 公式写进 `tv/DESIGN.md`；
2. 有一条**会失败的断言**钉住；
3. 有 `.workbuddy/` 下的无头探针可复测（现有 `_boss-ttk.cjs` / `_route-metric.cjs` 是先例）。

## 五、角色与怪物系统 【新功能 · P2】

### 设计内容

- **多怪兽架构** —— 卡牌绑定怪物，哥斯拉之外可扩展第二只怪。
- **结构复用** —— 怪与怪之间共用系统结构。
- **技能独立** —— 每只怪的技能各自独立。
- **技能与怪物解耦** —— 卡牌不绑死单体。

### 现有基础 —— 架构已预留

| 已具备 | 位置 |
| --- | --- |
| "怪物 → 形态 → 部件槽 → {样式,颜色,大小}" 框架 | `tv/appearance.js` |
| 每只怪独立的骨骼数据 | `tv/assets/monsters/<怪兽>/rig.data.js` |
| 路径唯一真源 | `tv/assets/asset-index.js` |
| 装配顺序（索引 → 骨骼 → 形态 → 装配 → 渲染） | `tv/index.html` |

### 改造范围

**多怪不需要重构** —— 只需再提供一份 `monsters/<新怪>/`。
真实成本在**美术资产**（第二只怪的全套骨骼与部件），不在代码。

「技能与怪物解耦」才是真架构改动，且**依赖第一节的战技卡先落地**。

## 六、风险与失败机制 【新功能 · 撞铁律 · 待决策】

### 设计内容（与前提冲突）

- **怪兽血条** —— 巨兽拥有生命值。
- **失败惩罚** —— 失败影响关卡进度、需要重新开始。
- **手点成本** —— 引入操作成本。

### 冲突说明 ⚠️

本节的全部内容与开篇三条铁律**正面冲突**（无血条、无死亡、无玩家操作）。

现有实现中，受击只有 `recoil .1s` + `hitFlash .18s` + `shake`，**不掉血、不中断**；
关底 Boss 血量 `bossMaxHp()` 已按「目标击杀时长 60 秒」反解，
**整套设计哲学就是保证"打不过"这件事不发生**。

### 若决定实施，代价清单

- 重写 Boss 血量语义（现锚在巨兽输出上，需改为锚在巨兽生存能力上）。
- 新增判负与回退流程。
- 存档新增 `hp` / `runLost` 字段，版本 4 → 5。
- "关掉再打开接着算"的行为需重新定义（现离线结算与失败状态互斥）。
- 需要**显式覆盖产品铁律**。

> **本节的定位：** 策略感可以不依赖风险感 —— 前五节的"配什么卡、什么顺序"
> 本身已构成策略空间。建议优先完成一至五节。

## 九、数值框架

> 按「数值必须给公式，不给魔数」的纪律，以下公式中的**标定系数**（形如 `CAL`）
> 均为占位，必须在实现时用无头探针实测标定；标定过程与结论一并写进 `tv/DESIGN.md`，
> 并配一条会失败的断言。

### 9.1 战技槽与充能轴

```js
// 槽位数：复用现有形态档锚点，不新造等级门槛
slots(L)   = clamp(1 + floor((L - 1) / 25), 1, 5)      // L1=1 · L25=2 · L50=3 · L75=4 · L100=5

// 充能轴：每槽独立充能，到点即可释放；同一拍多个可用时按槽序取第一个
charge_i  += dt × chargeRate_i                          // 每帧推进
ready_i    = charge_i >= cost_i
charge_i   = 0                                          // 释放后归零

// 空槽与未就绪时降级为普攻（普攻不占槽、无充能）
if (无槽可用) 执行基本攻击

// 效率 = 有卡覆盖的时间占比（"技能越多效率越高"的机制表达）
efficiency(L) = Σ(已装配且已就绪的槽) / slots(L)
```

**调参旋钮：** `chargeRate_i`（充能速度）与 `cost_i`（充能代价），两者合成"每隔几秒放一次"。

**初始基准：** 普攻间隔沿用现有爪击节奏（1.18s / 0.54s 命中）；
战技间隔从 `cost / chargeRate ≈ 4~6s` 起调。**具体值待实测标定。**

### 9.2 元素反应

```js
// 附着：命中时给目标挂状态（不落盘，不进存档）
target.status = { element, stacks, until: now + STATUS_TTL }

// 二元反应表：先附着 A，再命中 B
REACT[A][B] → { name, mult, aoe, ... }

// 倍率统一入口
reactMult = REACT[A][B].mult × (1 + 0.06 × 相关天赋等级)
```

**反应表初稿**（`mult` 待标定；`aoe` 复用现有 `chain` 的 280px / 2 目标通道）：

### 9.4 关卡循环

```js
// 一局 = 一章（5 个区域），章末结算
runMax      = 5                                        // 复用现有"一章 5 区"
T_target    = 240                                      // 秒，目标单局时长（4 分钟）
reloadSpeed = 1 + 0.08 × 快速装填天赋等级                // 满级 ≈ ×1.33 → 240/1.33 ≈ 180s（3 分钟）
T_clear     ≈ T_target / reloadSpeed

// 本局深度奖励（"越往后奖励越多"）
depth     = 本局已推进区域数 / runMax                    // 0 → 1
奖励倍率   = 1 + DEPTH_GAIN × depth                      // 拆楼与击破收益都乘它
```

**章末通关大赏：** `depth === 1` 时发放一次性奖励（"不打到底拿不到"）。
**形态沿用现有 `grant()`**，不新增发钞口。

> ⚠️ 现有单局实际耗时**未实测**。开工前第一步应用无头探针
> （参照 `.workbuddy/_boss-ttk.cjs`）量出当前值，再反解 `T_target` 的调参方向。

## 十、存档影响

> `progression.js` 当前 `version: 4`，`sanitize()` **同时接受 3 和 4**。
> 只把版本号改成 5 就等于把所有旧档判废、回落成 1 级、**且不报错**。

| 大类 / 条目 | 新字段 | 是否必须升版本 |
| --- | --- | --- |
| 战斗系统 · 战技轴 | `warbuild`（槽位装配与策略模板） | 是（4 → 5） |
| 战斗系统 · 元素反应 | 复用已有 `subElements` | **否** |
| 成长养成 · 主属性→体貌 | 复用已有 `hue` / `morph` | **否** |
| 属性克制 · 敌方属性 | 资产侧标注，不进玩家存档 | **否** |
| 关卡循环 | `runProgress` / `runRewards` | 是（4 → 5） |
| 风险失败 · 血条 | `hp` / `runLost` | 是（4 → 5） |

**硬约束（三条，缺一不可）：**

1. `sanitize()` 必须**同时接受 4 和 5**，旧档就地补默认值 —— **绝不判废**。
2. 任何派生种子必须**确定性**：沿用 `hashSeed(...)`，**禁用 `Math.random()` / `Date.now()`**。
3. 新字段一律**钳制**取值范围，入 `sanitize()` 的白名单。

**另需一条会失败的断言：** 存档键两侧必须是同一个字符串 —— 任何新增字段都要确认
`tv/game.js` 的 `SAVE` 与 `tv-preload.js` 的 `KEY` 仍然一致，
否则接管**静默失效**、进度写回 localStorage 而两端不报错。
