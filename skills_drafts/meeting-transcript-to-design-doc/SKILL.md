# 会议录音 → 版本设计文档

## 何时用

主人给一份录音转写（或口述讨论稿），要的不是「纪要」，而是**能拿去排期、能开工的设计文档**。
判别：如果产出里有「说话人 1」「00:02」这种痕迹，或者只有摘要没有现状映射，就是做错了。

## 三条心法

1. **穷举在前，归类在后。** 先把每一句话里的提案抽全并编号，再往上归类。
   抽漏一条 = 漏一项需求，且不会有人发现。
2. **按「系统大类」归类，不按「功能点」。** 一个类目应当对应**游戏里的一整块系统**
   （战斗 / 属性 / 关卡 / 成长 / 角色 / 风险 / 多人），不是「一个功能」。
   经验值：**7 类左右，每类 1–7 个条目**。类目过十、每类一两个，就是拆细了 —— 必返工。
3. **每条提案都要回答「现在有没有」。** 给路径、给符号名。
   没有现状映射的文档，和一份空想提案没有区别。

## 步骤

1. **抽条目**：逐段读转写，把每个可命名的诉求抽成一条，编号。
   含"可以做/可以考虑"这类软表达的也要抽 —— 后续在优先级里处理，不在这里丢。
2. **判别性质**：每条标 **【新功能】**（项目里没有，要从零建）或 **【功能优化】**（已有基础，需扩展或补全）。
   ⚠️ **这一步必须查现状再标，不许凭描述猜。** 常见的错判见「血泪坑 5」。
3. **按系统大类收敛**：把条目挂到大类下。每类给「性质 + 包含条目 + 优先级」。
4. **逐条做现状映射**：查代码与文档，写清「已具备什么 / 位置 / 状态」。
   重点找**管道已铺好但没通电**的项 —— 这类是性价比最高的，必须显式标出。
5. **分离铁律冲突**：撞产品铁律的条目**单独成章**，不进优先级队列。
6. **排优先级**：按下面这套公开规则，并**把规则写进文档**（只给结论没人能复核）。
7. **给数值框架**：能定量的都写成公式；定不了的一律标**待实测标定**并给标定方法。
8. **评估存档影响**：新增字段 / 是否升版本 / 兼容策略。
9. **单列待决策事项**：把「需要人拍板才能往下」的问题集中成一张表。

## 优先级排序规则（照抄，别自创）

| 序 | 规则 | 理由 |
|---|---|---|
| 1 | **撞铁律的一律不进队列，先裁决** | 做完再推翻，成本翻倍 |
| 2 | **「通电」优先于「新建」** | 已有管道没接消费的，改动最小、收益最高 |
| 3 | **是别人前提的先做** | 例：技能卡是策略模板 / 元素反应 / 技能解耦的前提 |
| 4 | **与现有实现重合度高的先做** | 重合约 80% 的一类，改动量远小于听起来 |
| 5 | **纯表现层最后做** | 等数值定型再上，否则返工两次 |
| 6 | **远期架构、与产品形态冲突的搁置** | 明确写"建议不做"，并给理由 |

## 输出骨架（固定，不要改顺序）

```
# <产品名> · 玩法设计文档
  └ 抬头：状态 / 范围 / 产品铁律 / 归类约定（3~5 行，精简）

## 提案总览 · 按游戏功能大类的归类 ★ 核心     ← 必须在最前面
  | 大类 | 性质 | 包含提案 | 优先级 |
  └ 分类小结（新功能几类 / 优化几类 / 撞铁律几类）
  └ 贯穿全程的设计原则（不是条目的那几条）

## 一、<大类> 【性质 · 优先级】
  ### 设计内容      ← 这块要做什么
  ### 系统构成      ← 模块表（模块 / 说明 / 性质）
  ### 现有基础      ← 现状映射，带路径
  ### 改造范围      ← 差距清单，标 ⚠️ 风险点
  （多个大类重复此结构）

## 制作计划          ← 分期总表 + 每期清单 + 设计原则
## 数值框架          ← 逐模块给公式
## 存档影响
## 待决策事项
```

**总览表是最重要的一节** —— 它是全案的索引。放在文档末尾 = 等于没有。

## 血泪坑

### 1. 分类粒度拆细了必返工
主人原话：**「你整个拆太细了」**。
第一版按「功能点」分成 7 簇 22 条，被要求重做成「按游戏功能大类」。
⇒ 判据：**一类 = 一整块系统**。战斗 / 属性 / 关卡 / 成长 / 角色 / 风险 / 多人。
每类条目数 1–7 是健康区间。

### 2. 总览表必须在文档最开头
主人明确要求：**「这个很重要。要保留，并且在文档的最开头。作为本次提案的总结。格式也需要保持」**。
⇒ 表格的列头、行内容、性质标注、优先级写法一旦给定，**原样保留，不要美化、不要改词**。

### 3. 会议痕迹要清干净，但信息不能丢
要去掉：说话人身份、时间戳引用、「原话」引号、会议摘要段、关键词栏。
要保留：**分歧点**。把它从「谁反驳了谁」转写成「待决策事项 Q1/Q2…」。
⇒ 判别：留下来的是**设计输入**还是**过程记录**。前者留，后者删。

### 4. 条目数口径要自洽
抬头写「N 条提案」而表里逐项加起来不是 N，一定会被发现。
**成因**：按「提案编号」计 和 按「功能条目」计 会差数（合并同类项、拆开混装项）。
⇒ 落笔前把表里每一格数一遍。口径不同的，在抬头注明。

### 5. 「新功能」里藏着「通电」项 —— 必须查消费者
最容易误判的一类：描述听起来是全新系统，实际上**字段早已存在、早已落盘，
只是没人读**。例：`subElements` 字段齐全，但只有 `'pyro'` 一个 key 被消费 ——
需要的是「接通消费端」，不是「从零新建」。
⇒ 逐个字段 grep 读取点。**别信描述，信消费者。**

### 6. 铁律冲突项不许按普通优先级排
撞产品铁律的（如无死亡 / 无操作 / 不可失败）不能写进 P0/P1 队列。
单独成章，标明冲突条款，并给**实施代价清单**（要改哪些既有契约、是否要升存档版本、
是否需要人显式覆盖铁律）。同时给一句立场，并说明"不做它也能达成目标"的替代路径。

### 7. 数值不许编
每个数字要么给公式（含推导来源），要么标 **待实测标定** + 标定方法
（用无头探针量出当前值，再反解目标）。
**标定系数写成 `CAL` 这类占位符**，并写明「实现时用探针标定，结论回写设计文档 + 配一条会失败的断言」。

### 8. 现状映射要带路径
「已有基础」一节必须能被复核：写文件名、函数名、字段名、行号（有就写）。
只写「目前已有类似功能」等于没写。

## 自检

- [ ] 条目是**逐句抽全**的，没有整段漏掉？
- [ ] 归类是**按系统大类**（约 7 类），不是按功能点？
- [ ] **每一条**都标了【新功能】/【功能优化】？
- [ ] 每一条都有**现状映射**（带路径 / 符号名）？
- [ ] 「通电」项（已有管道没接消费）**已单独标出**？
- [ ] **总览表在文档最开头**，格式与给定的一致？
- [ ] 优先级附了**排序规则**，不只是结论？
- [ ] 撞铁律的**独立成章**，没混进优先级队列？
- [ ] 数值都有公式，标定系数标了占位 + 标定方法？
- [ ] 存档影响评估了（新字段 / 版本 / 兼容）？
- [ ] 会议痕迹清干净了（无说话人 / 时间戳 / 纪要段）？
- [ ] 待决策事项单列成表，每条给了建议？
- [ ] 表里逐项加起来的数 = 抬头写的数？

## 项目锚点（巨兽都市 · Godzilla）

> 换项目时替换本节即可，上面通用部分不动。

**产品铁律（冲突项判定依据）：** 无血条、无死亡、无玩家操作；任何设计不得引入失败状态。

**含义约定：** 【新功能】= 从零建 · 【功能优化】= 已有基础需扩展补全 ·
P0 立即可开工 · P1 第一期 · P2 第二期 · P3 搁置。

**文档落位：** `doc/game-design/`。写入后必须同步 `doc/README.md` 的目录树与阅读顺序
（那里逐条列了每个文件的状态，不同步就会留下过期描述）。

**数值纪律：** 公式写进 `tv/DESIGN.md`；配一条会失败的断言；
用 `.workbuddy/` 下的无头探针复测（现有先例 `_boss-ttk.cjs` / `_route-metric.cjs`）。

**改 `tv/` 的前置条件：** `godzilla-pet/tv/` 是「被播放的画面」，
改动等于改产品定义 —— 必须显式提出，不能顺手改。
