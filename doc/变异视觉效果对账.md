# 巨兽都市 · 突变视觉效果对账

**状态：审计结论（2026-09-20）** —— 只记录现状与缺口，不含设计意图。
**复现方式：** `node godzilla-pet/tv/tests/mutation-visual-audit.cjs`

---

## 一句话结论

突变池 41 条里，**只有 23 条真的改变了屏幕画面**；8 条只改了数值、画面不动；
**10 条完全失效** —— 视觉没人画、数值没人读，抽到等于没抽。

---

## 判定口径

一条突变「生效」的定义：它写进 `morph` / `subElements` 的**至少一个字段**，
在渲染或数值链路上有真实读取点。

数据的唯一流向是：

```
progression.js MUTATIONS[].apply()         写入
   └→ data.morph / data.subElements        存档快照（已落盘）
        ├→ appearance.js decor()           视觉声明表
        │     └→ game.js drawMorph() / drawHologramDecor()   真正绘制
        └→ progression.js Economy.*()      数值消费
             └→ growth.js growFactor() / spineBonus()
```

消费点全部由审计脚本用「逐条 apply → 字段增量 → 消费者查表」的办法实测得出，
不是读注释得出的。表在 `tv/tests/mutation-visual-audit.cjs` 的 `CONSUMER` / `SUB_CONSUMER`。

三档判定：

| 判定 | 条数 | 含义 |
| --- | --- | --- |
| `visual` / `visual+numeric` | 23 | 画面真的会变 |
| `numeric` | 8 | 画面不变，但数值真的被读，玩家能从战斗力感受到 |
| `inert` | 10 | 画面不变、数值也没人读 —— **抽到等于没抽** |

## 三、部件级覆盖：声明 9 个部位，只有 3 个真的有外观

突变定义里的 `part` 字段只用于横幅文字（`game.js:966` 的「部位 xxx」），
**没有任何断言保证它和真正被绘制的骨骼槽一致**。逐部位核对：

| 声明部位 | 相关突变 | 部件级外观是否落地 |
| --- | --- | --- |
| `spikes` | `p_spike1/2/3/4` | ✅ 根数 / 高度 / 分叉都画（`rig.js` FinRenderer） |
| `head` | `p_horn`, `p_horn2`, `p_lidless`, `p_eye3` | ✅ 头角、眼部红光、第三眼都画 |
| `torso` | `p_scale`, `p_frill`, `p_bulk` | ✅ 鳞甲分块 + 体型 |
| `tail_mid` | `p_tail`, `p_tailfin` | ❌ 尾节数量从未参与绘制 |
| `tail_tip` | `p_tailtip` | ❌ 锤状尾尖从未绘制 |
| `tail_base` | `p_twin_tail` | ⚠️ 视觉落在 `tail_tip`，与声明部位不一致 |
| `forearm` | `p_claw` | ❌ 爪子数量只进读数文字 |
| `jaw` | `p_jaw` | ❌ 完全无效果 |
| `thigh` | `p_thigh` | ❌ 只给速度数值 |

## 四、外观身份撞车

`hue` 是「体色」的唯一开关，`appearance.js` 的 `hueStyles` 只有 4 个值，
而突变的 `hue` 赋值有 6 处：

| `hue` 值 | 赋值来源 | 结果 |
| --- | --- | --- |
| `crimson` | `t_crimson` 赤化、`t_inferno` 炎狱体 | **两条传说突变的体色完全相同** |
| `jade` | `t_jade` 翠化、`t_glacial` 冰封体 | **两条突变体色完全相同** |

（`albino` → `t_albino`，`obsidian` → `t_obsidian`，无冲突）

## 五、顺带发现的死代码

1. **调色板整条轴失效。** `appearance.js` 的 `PALETTES`（`crimson/albino/obsidian/jade` 叠色）
   与 `toParts()` 写进部件的 `color` 字段，在渲染路径上**完全不生效**：
   `rig.js` 的 `Skeleton.draw()` 只做 `drawImage`，不做任何染色；而 `game.js:581`
   又明确禁止用矩形叠色。体色实际只靠 `skinFor()` 换整套贴图生效（`hueStyles`）。
2. **`decor()` 的输出有 3 个没人收。** `plates.count`、`claw.count`、`bonus` 都没有绘制消费点；
   `overlay` 被显式弃用。
3. **`decor()` 的声明表漏了 3 个视觉字段。** `tailSegs`、`tailTip`、`elemental`
   从 progression 写入后，**没有进入 `decor()` 的输出**，也就断了唯一的外观通道。

---

## 六、根因

不是「某个函数忘了加一行」，是三层之间**没有会失败的断言**：

1. `progression.js` 可以往 `morph` 写任意字段，没人校验它有消费者；
2. `appearance.js` 的 `decor()` 可以漏转发字段，没人校验「progression 写的视觉字段 ⊆ decor 的输出」；
3. `game.js` 可以只画 `decor()` 输出的一部分，没人校验「decor 的输出 ⊆ game.js 的绘制」；
4. `part` 字段与真实绘制的骨骼槽之间没有任何约束。

每一层都静默通过。这正是 SOUL.md 里那条「跨进程、跨文件、跨语言的隐形契约，
必须有一条会失败的断言盯着」要防的情形。

---

## 七、建议（按性价比排序）

**第 1 步：把审计脚本接成门禁。**
`tv/tests/mutation-visual-audit.cjs` 已经能算出每条突变的判定。加一个断言：
`audit().filter(r => r.verdict === 'inert')` 必须为空 —— 现在会红 10 项，正是要修的清单。

**第 2 步：补齐 `decor()` 声明表（低成本、收益最高）。**
把漏掉的 3 个字段接进去，并把 `game.js` 已有的绘制补上：

| 字段 | 落地方向 |
| --- | --- |
| `elemental` / `elementBoost` | 复用 `drawMorph` 的 aura 通道，用主元素色出粒子；`elementBoost` 乘进 `atomic()` |
| `tailTip === 'hammer'` | 在 `drawMorph` 里按 `tail_tip` 骨骼画一个方形尾锤（与 `D.tail.twin` 同一处） |
| `tailSegs` | 给 `rig.js` 的 `FIN_ANCHORS` 式做法加一组尾节锚点，或直接把 `tail_mid`/`tail_tip` 部件按 `1+n×0.06` 拉长 |
| `crit` | 在 `damageEnemy()` 里加一次 `hashSeed` 派生判定（禁用 `Math.random`），命中时出暴击数字 |
| `hitFlash` | 把 `game.js` 的 `hitFlash` 变量乘上 `data.morph.hitFlash ?? 1` |
| `pressResist` | 乘进 `pressure()` 的返回值 |
| `meleePenalty` | 乘进 `doClaw()` / `doTail()` 的伤害 |
| `jawBoost` / `clawBoost` / `tailBoost` | 分别乘进撕咬、爪击、尾扫的判定范围或伤害 |
| `volt` / `cryo` / `magma` / `venom` | 在 `updateBeam` 的命中分支里按 key 出副特效（`arcs` 通道已有 `chain` 的先例） |

**第 3 步：给 `part` 字段加对账。**
在 `appearance.js` 的 `validate()`（已有形状态与 EPOCHS 对账的先例）里增加一条：
每个突变声明的 `part` 必须能在某个绘制函数里被找到，找不到就报问题。

**第 4 步：给 `hue` 加法条或改色相参数。**
4 个 `hueStyles` 装不下 6 处赋值。要么给「炎狱体 / 冰封体」各开独立贴图，
要么把 `hue` 从枚举改成色相偏移量，让任意条数都能区分。

## 附：判定口径的两个已知边界

1. 审计脚本按「字段有没有读取点」判定，**不判断效果量级是否可见**。
   例如 `p_bulk` 的 `extraScale=0.015` 有读取点，但在屏幕表观已吃满 2.04 的高等级下
   会被镜头反向收敛抵消（见 `growth.js` 的 `VIEW.ceiling`），实测可能看不出差别。
2. `numeric` 档不代表「设计上应该有外观」。属性类突变（`m_*`）本来就不承诺外观，
   归入 `numeric` 是合格的；`p_thigh` 这类挂在具体部位上的才需要追问。
