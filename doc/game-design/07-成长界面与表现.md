## 1. 目标

`06-成长系统.md` 定义了**成长是什么**：加点、天赋、随机突变。
这份文档定义**玩家怎么看见它、怎么点它**。

三件事：

1. 面板里加三个菜单：**加点 / 天赋 / 进化**
2. 加点 = 每级进化后给的加点机会
3. 进化 = 每级一次机会，点击后播**骰子滚动动画**

## 2. 三个必须遵守的架构约束

新 UI 不能另起一套。它必须长在现有面板框架上，而那个框架有三条已经写进代码和注释的规则
（`panel-preload.js` 头部的注释就是权威描述）：

| # | 约束 | 后果 |
| --- | --- | --- |
| A | **面板是「另一个 tv 实例」**，跑同一份 `game.js`，1:1 放大显示；电视窗口不动一个像素 | 新菜单就是给同一份页面加 DOM，不是新窗口 |
| B | **面板的存档只读** —— `setItem` 只更新内存，绝不落盘；落盘由电视窗口独占 | 面板可以自己算、自己画，但不能写 |
| C | **面板里的点击靠 `id` 转发给电视窗口执行**（`panel:tap` → 主进程 → 在电视窗口 `el.click()`） | **每一个可点元素都必须有 `id`**，否则点了等于没点 |

约束 C 还有一条隐藏要求（见 `main.js` 的 `panel:tap` 处理器）：

```js
if (!/^[A-Za-z][\w-]*$/.test(id)) return;   // id 会被拼进 JS，先挡一道
```

**新元素的 id 必须是 `[A-Za-z][\w-]*`**，不能用中文、不能用数字开头。
另外 `open-*` 前缀是**故意不转发**的（那表示"在这个窗口里打开面板"），
所以菜单 tab 的 id 不能用 `open-` 前缀 —— 用 `xxxTab`。

## 3. 菜单结构

### 3.1 现状

`tv/index.html` 里有两套导航，**面板里两套都可见**：

```
.pixel-dock        #open-stats 强化 / #open-skills 技能树 / #open-news 档案 / #open-settings 设置
                   ↑ 电视窗口里被 TV_HIDE_DOCK_CSS 藏掉，面板窗口里没藏
.research-bar .tabs  #statsTab 01 / #skillsTab 02 / #newsTab 03 / #settingsTab 04
                   ↑ 真正的面板内导航
```

> **顺手要修的一处重复**：面板里同时存在 `.pixel-dock`（右上角 4 个按钮）和
> `.tabs`（栏内 4 个 tab），两套导航表达同一件事。建议把 `TV_HIDE_DOCK_CSS`
> 也注入面板窗口（现在 `main.js` 只给面板注入了 `TV_DRAG_CSS`），
> 面板里只留 `.tabs` 一套。
> 注意：那会让"唯一改变画面呈现的注入"多一个生效窗口，`tests/tv.test.cjs`
> 里互相牵制的那两条断言要跟着核对。

### 3.2 新结构：6 个 tab

```
01 加点   #assignTab   ← 原「数值强化」重新定位（见 §4）
02 天赋   #talentTab   ← 新增
03 进化   #evoTab      ← 新增
04 技能树 #skillsTab   ← 现有，仅编号后移
05 档案   #newsTab     ← 现有
06 设置   #settingsTab ← 现有
```

对应的 panel 容器：`#assignPanel`（复用现有 `#statsPanel` 的 `upgrade-grid` 版式）、
`#talentPanel`、`#evoPanel`。

### 3.3 角标

`#assignTab` 和 `#evoTab` 在有未处理机会时显示右上角红点 + 数字：

```
#assignTab  可用加点 3   → 角标「3」
#evoTab     可用进化 5   → 角标「5」
```

**角标是这套 UI 的引擎。** 挂机游戏里玩家不看屏，回来时唯一能把他拉进面板的
就是"有几个东西在等我点"。而 3 个机会和 30 个机会的观感完全不同 ——
所以角标数字要**不加封顶地显示真实值**（挂机久了就是几十上百，
那个数字本身就是"我挂了很久"的凭证）。

## 4. 面板一 · 加点（`#assignPanel`）

### 4.1 加点机会从哪来

```
每升 1 级     →  +1 次加点机会
突破区域      →  +1 次加点机会（与 06 的 +2 突变点叠加）
```

**1 次机会 = 任选一项强化免费 +1 级**，不受核能价格限制，但受 500 级上限限制。

这和现有的「核能买强化」不冲突，两者分工清楚：

| 途径 | 货币 | 特性 |
| --- | --- | --- |
| 加点机会 | 升级白给 | **保底**：不看核能多少，升级就一定有成长 |
| 核能购买 | 核能 | **加速**：想快就花核能，价格按 `80/95/70/90 × 1.22^(等级-1)` 涨 |

> 这样设计的原因：现有系统里成长完全依赖核能（`upgrade()` 只看 `energy`），
> 于是"等级"本身只是个数字。加了加点机会之后，**升级这个动作终于有了直接产出**，
> 这正是主人要的「每个等级进化后加点」。

### 4.2 版面

沿用现有 `upgrade-grid` 的四行结构，每行加一个「加点」按钮：

```
┌──────────────────────────────────────────────────────────┐
│  可用加点机会   3                    [ 一键均分 ]          │
├──────────────────────────────────────────────────────────┤
│  巨兽力量   等级 12   (54 + 12×22) × M          53 核能   │
│  ────────────────────────────────────────────────        │
│  [ 加点 ]                                        [ 购买 ] │
├──────────────────────────────────────────────────────────┤
│  原子炉心   等级  8   (85 +  8×30) × M          84 核能   │
│  [ 加点 ]                                        [ 购买 ] │
├──────────────────────────────────────────────────────────┤
│  核能代谢   等级 10   …                         98 核能   │
├──────────────────────────────────────────────────────────┤
│  巨躯动能   等级  6   速度 30 + √6 × 8 = 49.6   72 核能   │
└──────────────────────────────────────────────────────────┘
```

| 元素 id | 作用 |
| --- | --- |
| `#assign_power` `#assign_atomic` `#assign_metabolism` `#assign_stride` | 花 1 次机会把该项 +1 |
| `#buy_power` … `#buy_stride` | 现有核能购买按钮（**保留不动**） |
| `#assignSpread` | 一键均分：把现有机会按"价格最低优先"分配完，用于机会攒多了以后快速清空 |
| `#assignAll` | 一键全投当前策略偏好项（对齐现有 `chooseUpgrade()` 的 `policy`） |

### 4.3 顺手要修的一处不一致

现有强化按钮**都是靠 DOM 顺序渲染的**，`game.js` 的 `buildUI()` 生成它们时没有 id。
而转发机制**只认 id** —— 也就是说，现在在面板里点「强化 +1」能生效，
大概率是因为页面里本来就有 id，或者这一条从来没被真正验证过。

> **落地前必须先核一遍**：把 `buildUI()` 生成的四个强化按钮、九个技能树节点的
> 真实 id 读出来，确认全部符合 `[A-Za-z][\w-]*`。
> 有任何一个没有 id，它今天在面板里就是**点了没反应**的 —— 属于现存缺陷，
> 顺手一起修。这是整份文档里最需要实测确认的一条。

### 5.3 节点状态

| 状态 | 视觉 | 可点 |
| --- | --- | --- |
| 未解锁（环未开启） | 整块打成斜纹噪点，进度条与文字压到 40% 不透明 | ✗ |
| 已解锁未点（0/3） | 空描边，进度条三格全空 | ✓（天赋点够时） |
| 已升级（1–2/3） | 实心格数 = 等级，节点边框变亮 | ✓ |
| 点满（3/3） | 边框加粗 + 角上小方块，进度条三格全亮 | ✓（不再可点） |
| **主元素** | 点满的元素节点额外加一个 `★` 与一圈外框 | — |

**主元素的判定**：元素环里**第一个点满 3 级的节点**成为主元素（`morph.element`）。
之后其他元素节点仍可点，只提供副特效，不改背刺颜色。判定结果落盘，不重算。

### 6.2 骰子 = 稀有度

**骰子面上的点数就是稀有度，面的颜色就是稀有度色。** 落定的那一刻，
不用读文字就知道中了什么。

| 骰面 | 颜色 | 稀有度 | 概率 |
| ---: | --- | --- | ---: |
| ⚀ 1 | 骨白 `#c8ccd4` | 常见 | 34% |
| ⚁ 2 | 骨白 `#c8ccd4` | 常见 | 26% |
| ⚂ 3 | 苔绿 `#7ddc8a` | 优良 | 25% |
| ⚃ 4 | 电蓝 `#6bb8ff` | 稀有 | 11% |
| ⚄ 5 | 幽紫 `#c58cff` | 史诗 | 3.5% |
| ⚅ 6 | 鎏金 `#ffd76b` | 传说 | 0.5% |
| — | — | **合计** | **100%** |

概率与 [`06-成长系统.md`](06-成长系统.md) §4.2 的权重表**逐个对齐**（常见 34%+26%=60%）。
骰子面出现的概率不均匀，但**骰子表面看不出概率** —— 这叫灌铅，
是唯一能同时满足"权重精确"和"骰子直觉"的做法。

**天气加成**：血月把高阶面的概率上浮 30%、静默 50%，即从常见面挪概率给高阶面。
界面上显示一行 `↓ 天气加成：血月 +30%`，让玩家知道**天气在改灌铅程度**。
骰子本体不动，改的是概率表 —— 这一点玩家能理解，因为天气一直在明处。

### 6.3 掷骰动画（核心表现）

**关键原则：结果在动画开始之前就已经确定了。**

```
点击 #rollEvo
  │
  ├─ ① 面板 preload 转发 id 到主进程
  │     panel:tap { id: 'rollEvo', kind: 'click' }
  │
  ├─ ② 主进程在**电视窗口**里 executeJavaScript 点击 #rollEvo
  │     ← 权威状态在这里，只有它算出来的突变才算数
  │
  ├─ ③ 电视窗口：rollEvolution() 用 seed+level 确定性地算出结果
  │     消耗 1 次机会 → 写入 mutations / morph → 立即 save()
  │     返回 { mutationId, name, rarity, face, part }
  │
  ├─ ④ 主进程把结果回推面板：panelWin.webContents.send('panel:rolled', result)
  │     ← 需要扩展现有的 panel:tap 处理器（见 §7.2）
  │
  └─ ⑤ 面板收到结果，播动画，**落在那个已知的面上**
```

动画时间轴（总长 1.85 s）：

| 段 | 时长 | 表现 | 骰面切换节奏 |
| --- | --- | --- | --- |
| 起转 | 0.00–0.45 s | 骰子整体轻微上抬 + 旋转抖动，切换时轻微模糊 | 每 60 ms 换一面（≈7 次） |
| 减速 | 0.45–1.25 s | 旋转幅度收窄，切换间隔逐渐拉长 | 90 → 130 → 190 → 270 ms |
| 落定 | 1.25–1.45 s | **停在目标面**（第 ④ 步已经知道是哪一面） | — |
| 确认 | 1.45–1.60 s | 骰子轻微下沉，该面颜色脉冲一次 | — |
| 展开 | 1.60–1.85 s | 结果卡片从骰子位置翻出：稀有度 + 名称 + 效果 + 部位 | — |

**稀有度加戏**（在展开之后追加）：

| 稀有度 | 追加表现 | 额外时长 |
| --- | --- | --- |
| 常见 | 无 | 0 |
| 优良 | 卡片边框亮一下 | 0.2 s |
| 稀有 | 卡片 + 一次轻微屏震 | 0.4 s |
| 史诗 | 卡片 + 屏震 + 骰子残留紫色余晖 | 0.8 s |
| 传说 | **全屏白闪 0.2 s + 骰子碎裂成金色碎片 + 专属音效** | 1.5 s |

### 6.4 连掷与自动

| 情况 | 行为 |
| --- | --- |
| 动画期间再点 `#rollEvo` | 按钮置灰。但**允许排队** —— 机会多时连点，队列依次播完（最多排 5 个） |
| 机会为 0 | 按钮置灰，显示"升级获得进化机会" |
| 切到别的 tab | 动画继续播完（不打断），但不再追加屏震类效果 |
| 面板被关掉（× / Esc） | 动画中断。**但结果已经落盘了**（第 ③ 步），下次打开时在「最近进化」里 |
| **自动进化开启**（默认） | 不弹骰子。在电视窗口的右下角播一个 **0.8 s 的骰子快闪角标**：小骰子快速滚 0.3 s → 停在结果面 → 淡出。挂机也能看见成长，但不打断观看 |

> 自动模式用"快闪角标"而不是完整骰子，是为了守住
> [`01-设计总纲.md`](01-设计总纲.md) 的支柱 1：**玩家不点也能一直前进。**
> 骰子完整动画是给"想看"的人准备的，不是必经流程。

### 6.5 无障碍与降级

| 项 | 处理 |
| --- | --- |
| `prefers-reduced-motion: reduce` | **跳过滚动，直接显示结果卡片**，只保留 0.2 s 淡入 |
| 键盘 | 骰子区 `role="status" aria-live="polite"`，结果文本自动被读屏播报 |
| 色盲 | 稀有度不能只靠颜色 —— 卡片上同时有**文字档位**与**骰面点数**两个冗余编码 |
| 快速模式 | `#evoSpeed` 切到「快速」后动画压缩到 0.35 s（保留落定与展开两段） |

## 7. 数据与转发

### 7.1 新增存档字段

在 [`06-成长系统.md`](06-成长系统.md) §7 的基础上增加两个：

```
assign     number   可用加点机会（新档 0）
evoRolls   number   可用进化机会（新档 0）
```

升级时的发放（都在 `progression.js` 的 `gain()` 循环里，与 `dna++` 同一处）：

```
level++  →  dna +1（现有）  assign +1  evoRolls +1
level % 3 === 0  →  天赋点 +1
突破区域  →  dna +2（现有）  assign +1
```

### 7.2 主进程要改的一处（`main.js` 的 `panel:tap`）

现在的实现**丢掉了 `executeJavaScript` 的返回值**：

```js
win.webContents
  .executeJavaScript(`(() => { ... return true; })()`)
  .catch(() => { /* 电视窗口还没就绪，这一下就算了 */ });
```

需要改成：把返回值接出来，若是对象就回推面板。

```js
win.webContents
  .executeJavaScript(`(() => {
    const el = document.getElementById(${JSON.stringify(id)});
    if (!el) return false;
    ${body}
    return el.__panelResult || true;      // 游戏侧把结果挂在元素上
  })()`)
  .then((r) => {
    if (r && typeof r === 'object' && panelWin && !panelWin.isDestroyed()) {
      panelWin.webContents.send('panel:rolled', r);
    }
  })
  .catch(() => {});
```

新增一条 IPC 通道：`panel:rolled`（主进程 → 面板）。
**这是这套设计里唯一新增的跨进程消息**，其余全部复用现有的 `panel:boot` / `panel:tap` / `panel:done`。

### 7.3 面板的一致性（必须处理，是现存缺陷）

面板的存档是只读的，它靠"同一份存档 + 同一串点击"和电视窗口保持一致。
但**电视窗口在面板开着的时候一直在跑**（会自动升级、自动加点、自动进化），
面板对此一无所知。于是面板上的数字会越来越不准。

今天这个问题不痛，因为面板只是"显示强化价格"。但新 UI 加了**角标**之后它就致命了：

> **角标永远不亮** —— 玩家挂机 8 小时回来打开面板，面板还以为自己有 0 次进化机会。

**修法：加一条周期性同步。**

```
主进程在电视窗口每次落盘（每 5 秒 + pagehide）后，
把 payload 推给面板：panelWin.webContents.send('panel:sync', payload)

面板收到后：用只读方式重建 economy（保留自身的 UI 状态），重渲染 DOM 与角标。
```

实现上建议**复用 `panel:boot` 的载荷形状**，面板侧写一个 `applySync(payload)`，
和启动时的初始化走同一个函数 —— 不写两套解析逻辑，否则迟早漂移。

> 也可以让电视窗口主动广播，但那样电视窗口就要知道面板存在，
> 破坏了"桌宠只管窗口生命周期"的分层。**从主进程推更干净**，
> 因为面板窗口本来就是主进程创建的。

### 7.4 掷骰的确定性（不能破）

`06-成长系统.md` §6 的 `mutateFor(seed, level, weather, talents)` 保持不变：

- 结果由 `seed + level` 确定性派生，**掷骰动画不参与计算**
- 已获得的突变落盘在 `mutations`，即使 `seed` 因为极端情况重新派生，
  已发生的外观也不会变
- **绝不能用 `Math.random()` 决定骰子落在哪一面。** 动画里那些"随机换面"
  可以用 `Math.random()`（它只是视觉噪点），但**最终停留在哪一面必须来自第 ③ 步的返回值**

这条要在测试里钉住：给定同一个 `seed + level`，连掷 100 次，
骰面分布应当收敛到 §6.2 的概率表，且同一 `(seed, level)` 永远得到同一面。

## 8. 视觉规范

| 项 | 值 |
| --- | --- |
| 面板尺寸 | 视口 1120 × 736，1:1 显示（`zoom = min(1, (可用高 − 32) / 736)`） |
| 字体 | Fusion Pixel（随包），字号 **12 / 14 / 16 / 20**，最小 12（面板是 1:1，不必再用 11） |
| 描边 | 整数像素，`1px` / `2px` / `4px`；**禁止半像素与模糊阴影** |
| 阴影 | 硬阴影 `Npx Npx 0 <色>`，与 `dock.html` 的按钮同一套语言 |
| 圆角 | **0**（像素风格）。骰子与卡片都是直角 |
| 骰子 | 16 × 16 点阵放大为 96 × 96（整数倍），点阵用 SVG `<rect>` 逐格绘制，**不用 canvas** |
| 稀有度色 | 见 §6.2；同时通过 CSS 变量暴露，便于统一改 |

> **骰子为什么不用 canvas**：面板页面上已经跑着 `game.js` 的 Canvas 2D 主循环。
> 再加一个 canvas 就要加一路 `requestAnimationFrame`，两个循环会在同一个
> 窗口里互相抢帧，而面板是 1:1 的——掉帧看得见。SVG + CSS transform 由合成器
> 处理，不吃主循环。
