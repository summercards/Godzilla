# 怪物成长形态框架 v1

> 适用：`tv/assets/monsters/` 下的所有怪兽，当前只有 `godzilla`。
> 代码实现：`tv/appearance.js`（形态解算） + `tv/assets/asset-index.js`（资产清单）。
> 目录与命名约束见 [资产规范.md](./资产规范.md)。

---

## 1. 为什么要有这个框架

改造前，"怪兽长什么样"这件事散在三个地方，互相不知道对方存在：

| 位置 | 管什么 | 问题 |
| --- | --- | --- |
| `rig.js` 顶部的 `PARTS` 字面量 | 12 个部件的路径、尺寸、枢轴 | 路径写死，加形态要改代码 |
| `game.js` 的 `drawMorph()` | 背鳍、角、眼、护甲、辉光、体色 | 18 行内联分支，加体征要改这条函数 |
| `progression.js` 的 `EPOCHS` / `morph` | 等级阈值、突变数据 | 只有数值，没有"这个突变改哪个部件的哪一面" |

框架要解决的就是：**把"怪物长什么样"变成一张可声明、可校验、可被美术接手的数据表**，
并且让进化过程只改表，不改渲染代码。

## 2. 三层结构

```
怪物 Monster
 └─ 形态 Form           5 档，与 EPOCHS 一一对应
    └─ 部件槽 Slot      12 个骨骼槽 + 7 个装饰槽
       ├─ 样式 style    换贴图
       ├─ 颜色 color    调色板
       └─ 大小 size     绕枢轴等比缩放
```

### 2.1 怪物

怪兽的身份与资产根目录。当前只有 `godzilla`（哥斯拉）。
登记在 `asset-index.js` 的 `MONSTERS`，含显示名、图标、槽位清单、已登记的样式。

### 2.2 形态

**形态 = 等级阶梯的呈现层**，不是第二套成长曲线。

- 等级 → 形态的**阈值**只由 `progression.js` 的 `EPOCHS` 决定：
  幼兽 `@1` → 亚成体 `@25` → 成体 `@50` → 完全体 `@75` → 灾厄体 `@100`。
- 形态 → 外观的**呈现**只由 `appearance.js` 的 `FORMS` 决定，按**序号**与 `EPOCHS` 对齐。
- `appearance.js` 不声明任何等级数字。两边长度与名称的一致性由
  `Appearance.validate(EPOCHS)` 在测试里强制对账 —— 改了一边忘了另一边会直接测试失败。

这样做的原因：如果形态自己再写一套阈值，就会出现"第 25 级该变成亚成体还是成体"
两个答案，这种分歧是后期最难查的一类 bug。

### 2.3 部件槽

槽位分两类。这个区分很重要：**骨骼槽动结构，装饰槽只叠加。**

#### 骨骼槽（12 个，硬契约）

与 `rig.js` 的 12 个变换节点一一对应。槽位名同时就是
`assets/monsters/<怪兽>/parts/<槽位>/` 的目录名。

| # | 槽位 | 说明 |
| --- | --- | --- |
| 1 | `head` | 头（不含下颌） |
| 2 | `jaw` | 下颌 |
| 3 | `torso` | 躯干（含近侧臂根、腿根） |
| 4 | `upper_arm` | 上臂 |
| 5 | `forearm` | 前臂**含手与爪** |
| 6 | `thigh` | 近侧大腿 |
| 7 | `shin` | 近侧小腿**含脚** |
| 8 | `far_thigh` | 远侧大腿 |
| 9 | `far_shin` | 远侧小腿**含脚** |
| 10 | `tail_base` | 尾根 |
| 11 | `tail_mid` | 尾中 |
| 12 | `tail_tip` | 尾尖 |

两个容易踩的点：

- **没有独立的 `hand` / `foot` 槽。** 手和爪的像素在 `forearm.png` 里，脚在
  `shin.png` / `far_shin.png` 里。想单独换手或换脚，得先改母图拆件，不能凭空加槽位。
- **左右是"近侧 / 远侧"，不是"左 / 右"。** 因为怪兽永远朝一个方向走，
  `far_*` 是被躯干挡住的那条腿，只有大腿和小腿、没有臂。

父子关系（`rig.json` 的 `slots[*].parent`）：
```
root → torso
        ├─ head → jaw
        ├─ upper_arm → forearm
        ├─ thigh → shin
        ├─ far_thigh → far_shin
        └─ tail_base → tail_mid → tail_tip
```

绘制顺序（`rig.json` 的 `order`，后画的盖前面的）：
```
tail_tip → tail_mid → tail_base → far_thigh → far_shin → torso
        → thigh → shin → upper_arm → forearm → jaw → head
```

#### 装饰槽（7 个，可选叠加）

不参与骨骼，画在身体轮廓之上。目前由 `game.js` 的 `drawMorph()` 程序化绘制，
未来可以逐个替换成贴图。

| 槽位 | 当前载体 | 受什么驱动 |
| --- | --- | --- |
| `spikes` | 沿尾尖→头部脊线分布的三棱背鳍 | 形态 `EPOCHS[].spikes` + 天赋 `spines` + 突变 `spikes`/`spikeScale` |
| `plates` | 躯干 3×3 深色护甲分块 | 突变 `plates` |
| `horns` | 头顶角（1 或 2 根） | 突变 `horns` |
| `eye` | 眼部红光 / 第三只眼 | 突变 `eyeGlow` / `thirdEye` |
| `aura` | 环绕躯干的元素光点 | 突变 `aura` + 天赋 `radiant` |
| `claw` | 爪（目前只记录数量，未单独绘制） | 突变 `claws` |
| `tail_fin` | 双尾 | 突变 `twinTail` |

### 2.4 三个轴

| 轴 | 取值 | 落点 | 当前状态 |
| --- | --- | --- | --- |
| **样式 style** | 样式名（`default` / …） | `parts/<槽位>/<样式>.png` | ✅ 已生效 |
| **颜色 color** | `none` / `crimson` / `albino` / `obsidian` / `jade` | `PALETTES` 调色板 | ⚠️ 已声明，见 §5 |
| **大小 size** | `0.85 ~ 1.25` 倍 | 绕枢轴等比缩放 | ✅ 已生效 |

## 3. 数据流

```
progression.js                 appearance.js               asset-index.js
  EPOCHS ──等级阈值──┐           FORMS ──按序号对齐──┐        MONSTERS / SLOTS
  data.morph ────────┤                                │        ENEMY_UNITS
  economy.epoch() ───┤          ┌─────────────────────┘        BUILDING_KINDS
  economy.mainElement┤          │                              dir/file 路径
  beamColor() ───────┘          ▼
                        Appearance.skinFor()            assets/monsters/godzilla/
                          → 每槽 { style, color, size }    ├─ rig.data.js（结构）
                                    │                     ├─ parts/<槽位>/<样式>.png
                          ┌─────────┴─────────┐           └─ source/（母图 + 裁切元数据）
                          ▼                   ▼
                   toParts()            decor()
                   rig.js 的 PARTS      drawMorph() 的画法
                   （12 骨骼槽）         （7 装饰槽）
```

一句话：**`appearance.js` 是唯一知道"哪个突变改哪个槽的哪个轴"的地方。**
`game.js` 只负责把解算结果画出来。

## 4. 现有突变已经挂上来的槽位

`progression.js` 的 41 个突变里，18 个 `cat:'part'` 突变**本来就带 `part` 字段**，
只是以前没人读它。框架把这批数据接上了：

| 槽位 | 挂载的突变 |
| --- | --- |
| `spikes`（装饰） | 脊刺增生 / 脊刺加长 / 脊刺晶化 / 脊刺分叉 |
| `head` | 头角萌生 / 巨角丛生 / 无睑之眼 / 血瞳 |
| `torso` | 躯干臃肿 / 鳞甲加厚 / 颈盾增生 |
| `tail_mid` | 尾节增生 / 尾鳍增生 |
| `tail_base` | 双尾 |
| `tail_tip` | 尾尖硬化 |
| `forearm` | 爪裂增生 |
| `jaw` | 獠牙外翻 |
| `thigh` | 腿肌隆起 |

**内容缺口**：`upper_arm`、`shin`、`far_thigh`、`far_shin` 这 4 个骨骼槽
目前没有任何突变挂上来。它们能换样式、能改大小、能被形态改，但玩家做什么都不会
单独改变它们 —— 这是可填的内容空间，不是 bug。

另外 16 个突变不针对单个槽位：`cat:'trait'`（9 个，改体色调色板 / 全局体型）、
`cat:'element'`（7 个，改辉光与主元素）。

## 5. 三个轴的落地程度（诚实版）

- **样式**：真的生效。解析出的路径会被 `rig.js` 的 `Skeleton` 加载，
  缺图时该部件不绘制（沿用既有行为）。
- **大小**：真的生效。改 `size` 只改 `scale` 与枢轴，
  关节世界坐标由 `rig.js` 的全局比例算，与单槽位大小无关 ——
  所以放大一个头不会把整只怪兽撑开，也不会把关节挪走。
- **颜色**：**对 12 个骨骼槽只记录、不施加。**
  原因：对已验收的像素部件做调色板重映射会改变轮廓边缘的抗锯齿表现，
  本项目有一条硬基线（"12 部件重组与原图 RGB 差 0"），本版不拿它冒险。
  目前真正生效的染色是装饰槽的**整体叠色**（`PALETTES[].overlay`）
  与辉光取色，也就是玩家在游戏里看到的"赤化 / 白化 / 玄化 / 翠化"。

  要真正启用骨骼槽调色，需要一格：在加载期把部件图画进离屏 canvas、
  按调色板重映射像素，再让 `Skeleton` 用重映射后的图。
  在那之前，`parts.<槽位>.color` 只是一个待用的声明。

## 6. 扩展流程

### 加一种样式（同一形态下的不同造型）
1. 产出 `parts/<槽位>/<样式名>.png`，**必须与 `default.png` 同像素尺寸**（见约束文档 §4）。
2. 在 `asset-index.js` 的 `MONSTERS.godzilla.styles` 里登记样式名。
3. 在 `appearance.js` 的 `FORMS[i].styles` 里把槽位指到这个样式名。
4. 跑 `npm test`：样式未登记、或引用了不存在的槽位，测试会直接红。

### 加一档形态
1. 在 `progression.js` 的 `EPOCHS` 里加一档（含 `min` 等级阈值）。
2. 在 `appearance.js` 的 `FORMS` 同序号位置加一条，`label` 必须与 `EPOCHS[].name` 完全一致。
3. `npm test`：两边长度或名称不一致会直接红。

### 加一只新怪兽
1. 建 `assets/monsters/<id>/` 全套目录，产出母图与 12 个部件。
2. 在 `MONSTERS` 里登记，改 `appearance.js` 的 `skinFor` / `toParts` 的默认怪兽（目前单怪兽硬编码在 `rig.js`）。
3. 注意：**10 级以上的改动**。当前 `rig.js` 只装配一只怪兽，多怪兽支持需要把
   `Skeleton` 的皮肤参数从 `game.js` 一路传下去，本版没做。

### 加一个敌人 / 一种建筑
见 [资产规范.md](./资产规范.md) §3.4 / §3.5。敌人加登记项 + 写 `draw<Name>` 函数，
建筑加登记项 + 写工厂函数；渲染分派都是查表，不用改分支链。

## 7. 校验

`npm test` 里的资产完整性测试把这套框架的约束变成可执行断言：

- `Appearance.validate(EPOCHS)` 返回空数组（形态与等级阶梯对账、样式与槽位引用合法）。
- 12 个骨骼槽在 `rig.json` / `asset-index.js` / 实际部件目录三方一致。
- `rig.json` 与 `rig.data.js` 与母图裁切元数据三者一致（`build/derive-rig.cjs --check`）。
- 每个登记单位的 `renderer` 都能被 `game.js` 解析到（漏写不会静默退化成坦克）。
- 每栋生成的建筑都指向一个登记的资产目录。
